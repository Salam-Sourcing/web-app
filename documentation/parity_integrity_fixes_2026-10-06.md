# Flutter/web parity fixes — 2026-10-06

The actionable D01–D07 and E01–E06 findings from the two October 6 audits have been addressed in the web and Flutter code. The necessary shared backend migration is applied. Browser push remains disabled and deferred at the user's request. This closes the recorded implementation findings; it does not certify every production/device workflow or equal security in every runtime path.

Both application repositories remain on branch `1.0`. These application changes have not been committed, pushed or released in this task. The hosted backend migration is live and supports older clients that omit the optional business request ID.

## Shared backend deployment

Applied to the existing Salam Sourcing project `stjtdlwonexcgnhmgfqw`:

- Migration: [`20261006221953_parity_integrity_guards.sql`](../../Salam-Sourcing-Marketplace-App/supabase/migrations/20261006221953_parity_integrity_guards.sql).
- Private, RLS-enabled request cache with client table privileges revoked, scoped by authenticated user and request UUID. The existing JSON RPC signatures accept an optional `client_request_id`; clients without it continue working.
- Current company permission checks run before replay. Suspended/revoked actors cannot recover another actor's intent through the cache.
- Decimal validation runs before the relevant RPC casts. A quote trigger rejects new or changed stored totals that are nonpositive; unchanged legacy zero/null totals remain manageable.
- Listing lead validation covers RPC and direct table writes while preserving unchanged legacy values.
- No customer records were rewritten or used as test fixtures. No quantity-scale change, push deployment or credential change was performed.

The four changed function definitions were compared with their earlier hosted hashes immediately before deployment; all still matched the inspected baseline. Deployment returned success. Read-only follow-up confirmed the hosted migration version, both guards, private-cache RLS, denied client cache reads, authenticated business RPC grants and denied anonymous/private-validator execution.

Security advisors show the existing one anonymous-summary and 68 authenticated-function execution notices unchanged. The intentional private request cache adds one informational “RLS enabled without policy” notice: clients have no table privileges or policies; guarded server functions own access. References: [private-table RLS notice](https://supabase.com/docs/guides/database/database-linter?lint=0008_rls_enabled_no_policy), [anonymous function execution notice](https://supabase.com/docs/guides/database/database-linter?lint=0028_anon_security_definer_function_executable), [authenticated function execution notice](https://supabase.com/docs/guides/database/database-linter?lint=0029_authenticated_security_definer_function_executable). This parity task did not perform a new repository-wide security scan.
